## 1. 文档目的

本 PRD 定义「健身动作指导」产品的需求、范围、验收标准与技术约束，供：

- **产品/设计**：对齐功能与优先级
- **开发（人）**：按模块分工与排期
- **AI 模型**：作为唯一需求真源（Single Source of Truth）进行实现与迭代

## 2. 产品概述

### 2.1 一句话描述

通过手机 App 或微信小程序，利用摄像头实时识别用户健身动作，**校验动作是否正确**，并**叠加/播放正确动作的动画指导**，帮助用户安全、规范地完成训练。

### 2.2 产品定位

| 维度 | 说明 |
|------|------|
| 品类 | AI 健身教练 / 动作表单纠错 |
| 核心差异化 | 实时姿态估计 + 可配置规则引擎 + **示范轨迹驱动的参考对照**（可再叠加详情示意） |
| 目标用户 | 居家健身者、健身房新手、需要动作纠错的自主训练者 |
| 最终交付形态 | **手机 App（iOS/Android）** 或 **微信小程序**（见 §5 平台策略） |

### 2.3 目标与成功指标

| 指标 ID | 描述 | MVP 目标 |
|---------|------|----------|
| KPI-001 | 单动作端到端延迟（摄像头 → 反馈） | ≤ 200ms（App）；≤ 400ms（小程序，含推理） |
| KPI-002 | 推理帧率 | ≥ 15 FPS（App）；≥ 10 FPS（小程序） |
| KPI-003 | 深蹲标准动作误报率 | < 15% |
| KPI-004 | 膝内扣等明显错误检出率 | > 80% |
| KPI-005 | 重复次数计数准确率（5 rep 测试） | 100% |
| KPI-006 | 首次进入训练（含模型加载） | < 20s（App）；< 25s（小程序） |

### 2.4 非目标（Out of Scope — MVP）

- 社交、社区、直播
- 完整课程订阅与支付体系
- 医疗级康复评估与诊断声明
- 多人同框同时指导
- 复杂解剖 3D 虚拟人实时渲染（详情预渲染片见 `FR-064`，**P2 延后**；训练指导不依赖其完成）
- 自动识别「用户在做什么动作」（MVP 用户手动选择，见 `FR-010`）
- 端到端「视频像素直接生成解剖成片」而不经轨迹/标准 Rig（非本阶段目标）

## 3. 用户与场景

### 3.1 用户画像（简要）

- **居家训练者**：无私人教练，需要即时纠错
- **健身房新手**：担心受伤，需要标准示范
- **进阶用户**：关注特定错误（如深蹲膝内扣、硬拉弓背）

### 3.2 核心用户旅程

```
打开应用 → 选择动作 → 阅读机位/setup 说明 → 授权摄像头
→ 倒计时 → 实时训练（骨骼叠加 + 纠错 + 参考动画 + 计数）
→ 结束 → 查看本次总结 → （可选）查看历史
```

| ID | 作为 | 我想要 | 以便 | 优先级 |
|----|------|--------|------|--------|
| US-001 | 用户 | 选择要练的动作（如深蹲） | 针对该动作获得专属校验 | P0 |
| US-002 | 用户 | 看到摄像头画面中自己的骨骼 | 理解系统正在跟踪我的身体 | P0 |
| US-003 | 用户 | 做错时立即看到哪里错了 | 马上改正，避免受伤 | P0 |
| US-004 | 用户 | 看到示范轨迹驱动的参考骨架叠在画面上 | 模仿标准动作幅度与节奏 | P0 |
| US-005 | 用户 | 自动统计完成次数 | 不用自己数 rep | P0 |
| US-006 | 用户 | 练完后看到本次总结 | 了解表现与常见错误 | P1 |
| US-007 | 用户 | 在微信里直接打开使用 | 免安装 App | P1 |
| US-008 | 用户 | 查看历史训练记录 | 追踪进步 | P2 |

## 5. 平台策略

### 5.1 双端目标

| 平台 | 角色 | 说明 |
|------|------|------|
| **手机 App（iOS + Android）** | 体验主阵地 | 端侧推理、低延迟、完整摄像头能力 |
| **微信小程序** | 获客与轻量使用 | 免安装；受限于包体与算力，架构可能含端云协同 |

### 5.2 技术路线（决策记录）

| 层级 | 手机 App（首选） | 微信小程序 |
|------|------------------|------------|
| 框架 | **React Native + Expo**（默认） | 原生小程序或 Taro/uni-app |
| 摄像头 | `expo-camera` 或 `react-native-vision-camera` | `<camera>` 组件 |
| 姿态推理 | **MediaPipe Pose**（端侧，`@thinksys/react-native-mediapipe`；需 Development Build） | 见 §5.3 |
| 共享逻辑 | `packages/core`：规则、角度、相位、计数（TypeScript） | 同左，打包进小程序 |
| 绘制 | Skia / Canvas 叠加层 | Canvas 2D |
| 动画 / 对照 | **示范轨迹 → 训练参考骨架**（FR-067/068）；详情预渲染片 P2 | 同左逻辑；小程序可后接 |
| 轨迹生产 | 离线工具链（本机/CI），非训练热路径 | 可选后接 |

> **AI Agent 注意**：业务逻辑（`FR-040`–`FR-053`、轨迹对照）必须写在**平台无关**的 `packages/core` 中，禁止在 UI 层硬编码规则。轨迹提取可放 `tools/`，产物由 core 消费。

### 5.3 微信小程序推理方案（已 Spike 敲定：方案 A）

**决策（Phase 0，2026-07-15）：选定方案 A —— 端侧 TFJS MoveNet Lightning，WebGL backend。** 符合 `FR-033`（视频本地处理、不上传云端），无需云端隐私授权。

| 方案 | 描述 | 优点 | 风险 | 结论 |
|------|------|------|------|------|
| **A** | TFJS + MoveNet（端侧 WebGL） | 纯端侧、隐私好 | 帧率可能不足 | ✅ **选定** |
| **B** | ONNX Runtime 小程序版 | 模型可控 | 集成复杂、包体限制 | 未采用 |
| **C** | 轻量化端侧 + 关键帧云端兜底 | 平衡体验 | 弱网体验差 | 备选（若 A 优化后仍不达标） |
| **D** | 全云端推理（腾讯云人体分析等） | 开发快 | 延迟、成本、隐私；违背 `FR-033` 时需产品签字 | 未采用 |

**Spike 实测（`nhwc-v11`，G4B/iOS 26.5 微信真机）**：全身 14-15/17 关键点、~4 FPS、稳态 ~350ms/帧。详见 `docs/spike-report.md`。

**关键实现约束（供 M2B `packages/pose-mp` 复用）**：
- 微信 `device_util.isBrowser()===false`，webgl 包不会自动 `registerBackend`；需 `wx.createOffscreenCanvas` + `setWebGLContext` + 手动 `registerBackend('webgl', ()=>new MathBackendWebGL(new GPGPUContext(gl)), 2)`。
- CPU backend 的 `execute` 同步会堵死主线程，**必须走 WebGL**。
- 模型 ~4.5MB 不进主包（80051 限 2MB），运行时下载至 `USER_DATA_PATH` 缓存。

**待优化(不阻塞 Phase 0，落在 M2B / VT-P2-005)**：~4 FPS 低于后续 ≥15 FPS 目标。优化阶梯见 `spike-report.md`（降分辨率 → 确认 WebGL2 → 复用张量 → 必要时降级 KPI 或启用方案 C）。

**MVP 决策门**：✅ 已于本版本 0.2.0 达成。

### 5.4 开发顺序建议

```
共享 core 规则引擎 → App 端侧闭环（MVP）→ 小程序移植/适配 → 体验对齐
```

Web 仅作为 **开发调试工具**（可选），**不是**最终交付形态。

```
│   ├── pose-mp/               # 小程序姿态推理适配
│   └── render/                # 骨骼绘制逻辑
├── apps/
│   ├── mobile/                # Expo React Native
│   └── miniprogram/           # 微信小程序
└── tools/
    └── dev-web/               # 可选：浏览器调试 pose+core
```

### 7.3 核心数据模型

```typescript
// 动作定义
interface Exercise {
  id: string;
  name: string;
  description: string;
  cameraHint: "front" | "side";
  rules: Rule[];
  phases: Phase[];
  keyframes: PoseKeyframe[];
  repConfig: RepConfig;
}

// 校验规则
interface Rule {
  id: string;
  joints: [number, number, number];
  metric: "angle" | "distance_ratio" | "horizontal_deviation";
  min?: number;
  max?: number;
  target?: number;
  tolerance: number;
  severity: "warning" | "error";
  message: string;
  activePhases: Phase[];
}

// 校验结果
interface ValidationResult {
  status: "correct" | "warning" | "error";
  issues: Issue[];
}

// 训练会话
interface Session {
  id: string;
  exerciseId: string;
  startedAt: number;
  endedAt: number;
  reps: Rep[];
  topIssues: string[];
}
```

## 9. 界面与体验（UI / UX）

> 完整规格见 `docs/UI.md`、令牌见 `docs/design-tokens.md`。  
> UI 分三层，在**不同模块**落地，不是全部堆到 M4。

### 9.1 UI 三层与模块对应

| 层级 | 内容 | 开发模块 | 何时必须定稿 |
|------|------|----------|--------------|
| **L1 设计基础** | 设计令牌、线框图、组件清单 | **MU** | M3 开始前 |
| **L2 训练叠加层** | 摄像头上骨骼/ghost/反馈条/站位引导 | **M3** | M4 开始前 |
| **L3 应用页面层** | 动作库、详情、准备、总结 | **M4 / M5** | M6 前 |

```
M0 → MU（与 M1 可并行）→ M3 用 L1+L2 → M4/M5 用 L1+L3
```

## 10. 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| 小程序端侧算力不足 | 卡顿、延迟超标 | Phase 0 Spike；必要时云端方案 + 明示隐私 |
| 不同机型摄像头差异 | 跟踪不稳 | 多机测试清单；降分辨率 |
| 体型差异导致误报 | 体验差 | 可配置容差；严格度设置 |
| 宽松衣物干扰 | 关键点漂移 | 穿着提示；置信度过滤 |
| 侧面机位难摆 | 校验失效 | 强引导 UI + 示例图 |

## 12. 术语表

| 术语 | 定义 |
|------|------|
| Landmark | 姿态模型输出的单个人体关键点 |
| Ghost / 参考骨架 | 训练中半透明的**示范姿势骨架**（现由示范轨迹驱动，非手调关键帧） |
| 示范轨迹 | 从示范视频提取并清洗后的关节时间序列，按动作 ID 归档 |
| Phase | 动作阶段（如深蹲底部） |
| Rep | 一次完整重复 |
| ROM | Range of Motion，动作幅度 |
| 容差 | 规则允许的误差范围（度或比例） |
| visibility | 关键点可见度置信度 0–1 |
